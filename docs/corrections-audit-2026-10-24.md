## Deuxième lot — suggestions et devis

- **A05 : création atomique.** Create et Update sérialisent dans un fichier temporaire du même dossier, exécutent Flush(true), puis déplacent le fichier terminé. Create refuse tout écrasement. Les temporaires d’une opération échouée sont nettoyés ; les fichiers déjà enregistrés sont conservés.
- **A06 : conflits d’édition.** Revision optionnelle, égale à zéro pour les anciens JSON. Sous ProfileMutationLock, Update relit puis compare la révision avant écriture ; seule une sauvegarde réussie l’incrémente. L’interface transmet la révision chargée, garde les saisies et le brouillon en cas de conflit et actualise l’historique. Le rollback du changement de code client utilise la révision renvoyée. La corbeille d’un devis prend le même verrou.
- **A12 : historique complet.** Recherche sur tous les devis lisibles par nom, client ou référence, sans distinction d’accents/casse ; rendu par groupes de 20 avec Afficher plus de devis. Le filtre travaille en mémoire. Les brouillons restent visibles et les fichiers illisibles signalés.
- **Retour visuel utilisateur :** suggestions d’entreprises et d’adresses harmonisées avec la palette bleu nuit. Nom et détails séparés, textes plus grands, états de survol thématisés ; comportement de remplissage conservé.

### Limites du deuxième lot

Le verrou coordonne les processus locaux participants, pas les écritures simultanées distribuées par Nextcloud ni un éditeur externe ignorant les révisions. Les montants historiques sont lus tels qu’enregistrés. Un arrêt brutal peut laisser un temporaire ignoré par l’historique ; l’atomicité dépend des garanties du système de fichiers. Les tests simulent une erreur de sérialisation, sans simuler de panne matérielle.

Le chargement lit encore les fiches de devis en arrière-plan ; la pagination limite le nombre de contrôles créés et ne constitue pas une virtualisation de toutes les pages. Les constats A03/A04 restent à traiter. Huit constats de l’audit initial restent ouverts après ce lot.

## Troisième lot — fluidité (A03/A04)

- **A03 : création des contrôles bornée.** PagedRows construit au plus 50 lignes dans les pages projets, clients, collections, filaments et imprimantes. Les filtres et tris précèdent la pagination. Compteur et navigation au-dessus et sous les grands tableaux ; aucune barre sur les petits catalogues. Le contexte de filtre/tri/atelier détermine la remise à zéro ; une modification avec le même contexte conserve la page. La page est bornée si le catalogue diminue.
- **A04 : sauvegarde automatique hors UI.** Le timer capture un DTO détaché sur le fil UI puis appelle le magasin dans Task.Run. EstimateDraftWriter sérialise les opérations, suit les révisions de saisie sauvegardées et ignore les anciennes. Les révisions de brouillon sont internes à la session, distinctes des révisions de devis. Les retraits sont coordonnés avec l’écriture ; un travail retardé ne peut pas recréer un brouillon consommé/supprimé. Les callbacks vérifient atelier, identifiant, révision et fermeture avant de modifier l’état visible.
- Le booléen touched garde son sens métier (« un brouillon existe ») pour la confirmation d’abandon. La révision sauvegardée évite les écritures répétées ; il n’est pas réutilisé comme drapeau de fichier sale.

## Quatrième lot — ressources 3D et tampon (A07/A08/A13)

- **A07 : vignettes hors UI et propriété des images.** ModelThumbnails.GetAsync déporte aussi les métadonnées, la lecture et le décodage des PNG déjà présents. Le même sémaphore borne le travail. Une demande annulée ne retourne pas son image ; un PNG corrompu peut être reconstruit depuis le modèle. CreateNameCell n’effectue plus de test disque avant de créer la ligne. Une réapparition recharge une image valide. Le grand aperçu reste déclenché au survol.

Le rendu GPU n’est pas présenté comme ayant subi une correction mémoire équivalente : le défaut audité concernait le secours logiciel.
- **A13 : protections communes aux deux nettoyages.** PurgeOlderThan et TrimToSize utilisent la même inspection, refusant les liens/jonctions sans parcourir leurs cibles, les fichiers .tmp/.crdownload même imbriqués, les fichiers ouverts et les chemins à conserver. Un dossier contenant un élément protégé est conservé. Les cibles de suppression récursive sont vérifiées comme descendants du tampon. Maintain matérialise une seule fois le keep et les opérations de nettoyage sont sérialisées.
- **Course annonce/nettoyage reproduite puis corrigée.** La stabilisation d’un téléchargement et l’extraction d’un ZIP sont protégées avant travail ; les fichiers proposés sont protégés avant les événements FileReady/BatchReady.
